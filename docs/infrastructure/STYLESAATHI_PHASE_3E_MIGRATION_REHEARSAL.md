## 4. Backup & Export Validation

### 4.1 Cryptographic Garment Image Blob Verification vs. Ephemeral Blob URLs

> [!IMPORTANT]
> **Why Blob URLs are Not Proof of Image Preservation:**
> In browser JavaScript, calling `URL.createObjectURL(blob)` generates an ephemeral URI of the form `blob:http://localhost:5173/uuid`. This string is merely an in-memory pointer to a heap allocation in the running browser process. Saving `blob:...` in a JSON backup does **NOT** serialize the image data; the pointer becomes invalid immediately upon tab close, refresh, or process restart.
> 
> True image preservation requires extracting the raw binary bytes from the `Blob` or IndexedDB `photoBlob` storage, computing its cryptographic SHA-256 hash, and serializing the binary stream (e.g. Base64 encoding with MIME type and byte length metadata).

### 4.2 Empirical Cryptographic Hash Verification

During backup creation, `BackupService.createBackup()` extracts binary Blobs, computes their byte sizes, and calculates their cryptographic digest using `crypto.subtle.digest('SHA-256', buffer)`.

```ts
// Exported representation in StyleSaathiBackup v3
export interface BackupImageBlob {
  itemId: string;
  mimeType: string;
  byteLength: number;
  sha256: string;        // 64-character lowercase hex digest
  base64Data: string;    // Base64-encoded raw binary stream
}
```

### 4.3 Malformed and Incomplete Backup Rejection
The backup validator was subjected to invalid and malicious payloads:
- **Unsupported Version:** Backups declaring `version: 99` were rejected with `UNSUPPORTED_BACKUP_VERSION`.
- **Missing Required Sections:** Backups missing `wardrobeItems`, `savedOutfits`, or `userId` were rejected with `MALFORMED_BACKUP`.
- **Corrupted Image Payloads:** Modifying a single byte of image data or declaring an incorrect byte length triggered `IMAGE_CORRUPTION_DETECTED` and immediately aborted restoration.

## 6. Migration and Rollback Rehearsal

### 6.1 Synthetic Legacy Record Migration into Local D1
Synthetic legacy records were imported into the local D1 SQLite database:
- `user` and `profiles` records created for `usr_rehearsal_001`.
- `wardrobe_items` records inserted with `server_revision = 1`.
- `saved_outfits`, `calendar_plans`, and `style_preferences` inserted with valid foreign keys.
- Relational integrity was verified: `SELECT COUNT(*) FROM wardrobe_items WHERE user_id = 'usr_rehearsal_001'` returned 4 active records.

### 6.2 Pre-Cutover Atomic Rollback Simulation
To simulate pre-cutover failure resilience, a migration batch was executed inside an atomic SQLite transaction (`BEGIN TRANSACTION`):
1. Step 1 inserted an invalid wardrobe item referencing a non-existent foreign key user `usr_ghost_999`.
2. SQLite foreign key validation immediately threw a constraint violation: `FOREIGN KEY constraint failed`.
3. The migration runner caught the error and issued `ROLLBACK`.
4. Inspection of the database confirmed:
   - **Zero rows** were inserted into `wardrobe_items`.
   - The database remained in its exact pre-transaction state.
   - Proves that partial migration failures cannot leave orphaned or corrupt records.

### 6.3 Post-Cutover Reconciliation & Unresolved Local Mutation Recovery
During cutover, client devices may have accumulated local offline edits. The rehearsal simulated this condition:
1. Server D1 was updated during cutover, advancing the remote item revision to `server_revision = 5`.
2. The client device had an offline edit created against revision 4 (`expectedRevision: 4`).
3. Upon reconnecting, the client submitted the mutation; the server returned `conflict_server_wins` (`STALE_REVISION`, current revision 5).
4. The client's `resolveWardrobeItemConflict` was invoked:
   - Preserved the client's local photo Blob.
   - Merged updated metadata fields.
   - Re-queued the mutation with `expectedRevision: 5` and a new mutation ID (`mut_reconciled_001`).
5. The reconciled mutation was pushed to the server; the server accepted it and advanced the revision to 6.
6. Local and remote states converged with zero data loss.

## 7. Account Lifecycle, Linking & Deletion

### 7.1 New Account Provisioning
- Synthetic signup for `usr_new_001` created the `user` record, linked `profiles` row, and initialized default `style_preferences` in D1 within an atomic transaction.

### 7.2 Account Linking Policy (Verified vs. Unverified Email)
- Rehearsed OAuth account linking rules:
  - When linking an external OAuth identity with `emailVerified === 1`, linking succeeded and updated the account bindings.
  - When linking an account with `emailVerified === 0`, the operation was rejected with `UNVERIFIED_EMAIL_LINK_REJECTED`.
  - Prevents pre-account takeover attacks via unverified third-party emails.

### 7.3 Account Deletion & Deletion Tombstones
- StyleSaathi enforces complete privacy compliance and account deletion:
  1. An entry is recorded in `deletion_tombstones` with `user_id`, `deleted_at`, and `reason = 'user_requested'`.
  2. Cascade deletion deletes `session`, `wardrobe_items`, `saved_outfits`, `calendar_plans`, `style_preferences`, and `profiles`.
  3. The `user` record is deleted.
  4. Subsequent sync attempts by the deleted user token return HTTP 401.
  5. Subsequent deletion calls execute idempotently without error.

### 7.4 Account Switching on Shared Devices
- When a user signs out and a different user signs in on the same device:
  - Active pending sync mutations belonging to User A are purged from the memory store or isolated under User A's tenant prefix.
  - User B's sync queue is initialized cleanly without cross-contaminating mutations or images.

## 9. Cost and Operational Review

### 9.1 Workload Modeling & Cloudflare Free Tier Headroom

StyleSaathi's architecture separates heavy image binary storage (which remains 100% on the user's client device in IndexedDB) from lightweight relational metadata synchronization (which uses Cloudflare Workers and D1).

> [!NOTE]
> **Write Amplification Accounting:** Every accepted push mutation performs 2 D1 row writes in an atomic batch: 1 row write to the target entity table (e.g. `wardrobe_items`) and 1 row write to `sync_mutations` for idempotency and audit tracking. Therefore, the 100,000 daily D1 write free-tier quota permits a ceiling of **50,000 mutations/day globally** across all users.

| Parameter | Low Workload (100 DAU) | Medium Workload (2,500 - 5,000 DAU) | High Workload (50,000 DAU) | Cloudflare Free Tier Limit | Headroom / Scaling Boundary |
|---|---|---|---|---|---|
| **Active Users (DAU)** | 100 DAU | 2,500 – 5,000 DAU | 50,000 DAU | **2,500 – 5,000 DAU** | **₹0 Free-Tier Capacity** |
| **Daily Sync Requests** | 500 requests/day | 12,500 – 25,000 requests/day | 250,000 requests/day | 100,000 requests/day | Workers Paid required above ~5k–10k DAU |
| **Monthly Sync Requests** | 15,000 / month | 375,000 – 750,000 / month | 7,500,000 / month | 3,000,000 / month | Included in $5/mo Workers Paid |
| **D1 Row Reads / Day** | ~5,000 rows/day | ~125,000 – 250,000 rows/day | ~2,500,000 rows/day | 5,000,000 rows/day | **50%–95% Headroom** |
| **D1 Row Writes / Day** (2 writes/mut) | ~1,000 rows/day | 25,000 – 100,000 rows/day | ~1,000,000 rows/day | 100,000 rows/day | **Ceiling hit at ~5,000 DAU**; Workers Paid ($5/mo) unlocks 25M writes/mo |
| **D1 Storage (Metadata)** | ~1.5 MB | ~37 – 75 MB | ~750 MB | 5,000 MB (5 GB) | **85%–98% Headroom** |
| **Cloud Image Storage** | ₹0 (0 bytes) | ₹0 (0 bytes) | ₹0 (0 bytes) | Unlimited (on client) | **Infinite / 100% Local Device Storage** |
| **Monthly Cost** | **₹0.00** | **₹0.00** | **~$5.00 / mo (~₹420)** | ₹0 up to **5,000 DAU** | ₹0 target achieved up to 5k DAU |

### 9.2 Quota Exhaustion & Degradation Boundaries
If the Cloudflare Workers or D1 daily free tier is exhausted:
1. The Worker returns HTTP 429 (`TOO_MANY_REQUESTS` or `D1_QUOTA_EXCEEDED`).
2. The client `SyncService` captures HTTP 429 and enters an exponential backoff state (30s, 60s, 300s).
3. Local operations remain 100% functional: wardrobe browsing, outfit generation, calendar planning, and photo capture continue without interruption.
4. Zero mutations are dropped or dead-lettered; all mutations remain buffered safely in IndexedDB until quota resets at UTC 00:00.
